# AWS sandbox readiness

This checklist prepares the selected EKS reference pilot in eu-west-1 using **two separate AWS sandbox accounts**: the EKS control-plane account and the customer workload account. Local Compose is for developer fixtures. This checklist does not authorise an AWS login, provisioning, resource mutation or a production rollout. Copy `deploy/sandbox-inputs.example.json` into ignored `work/sandbox-inputs.json` and resolve each applicable field with the operator. Keep passwords, bearer tokens, external-ID values and private keys out of this checklist, plans committed to Git and Helm values.

## Inputs to settle before provisioning

- Record separate, authenticated control-plane and customer AWS profile names. In the separately authorised rollout session, check each profile with read-only STS caller identity and compare it to its reviewed account ID before planning. Authentication and any SSO renewal are operator steps; this increment performs neither. Avoid root identities and static exported credentials.
- Attach a dated, reviewed cost estimate with its reviewer and source reference. Include EKS/workers, RDS, NAT, optional ALB, regional state and logs, retained evidence/versions/backups, and encryption keys for their full retention lifetime. A monthly alert budget does not substitute for this estimate. Do not provision with the example's unresolved estimate/OIDC/account inputs.
- Record two distinct 12-digit control-plane and customer workload account IDs, existing operator role, approved public VPN/operator CIDRs, nonoverlapping VPC CIDR, deployment name and namespace. Both Terraform stacks require their own `expected_account_id`; wrong-account credentials are rejected by the provider and caller-identity postcondition. The customer module rejects a trusted ingester/executor principal in its own account; platform customer-role allowlists reject roles in the control-plane account. Supply the exact roles from the other selected sandbox account. Empty platform allowlists remain valid during bootstrap. Keep Terraform `namespace` equal to the Helm installation namespace so IRSA trusts the intended service accounts.
- Record the accountable owner, RFC3339 pilot end, monthly alert budget and approved recipients. The platform creates an **account-wide** AWS Budget with actual alerts at 50/80/100 percent and a forecast alert at 100 percent. This includes untagged resources in the control-plane account. The separate customer workload account requires its own approved cost-alert arrangement; record it in `customer_cost_control`. The IAM-only customer module creates no budget. Alerts are not a spending cap; notification delay and existing account spend apply. `Owner`/`ExpiresAt` tags do not automatically shut anything down. The example's zero budget deliberately fails validation until replaced with an approved amount.
- Approve the default billable footprint: EKS; two On-Demand m6i.large workers with 50-GiB gp3 roots; Multi-AZ db.t4g.medium Postgres16 with 30-GiB storage growing to 100 GiB; one NAT/EIP; six KMS keys; evidence storage, logs and a 30-GiB ClickHouse disk. ALB is optional. Record the timebox and who reviews cost alerts. No autoscaler or automatic expiry teardown is installed.
- Provision a separate encrypted, access-restricted Terraform state bucket/key, KMS key and lock table. The customer-role stack needs its own state. State and `terraform show -json` output can expose external IDs and secret metadata: restrict local permissions and retain them only under ignored storage.
- Supply OIDC issuer and optional explicit JWKS URL, `finops` access-token audience, public PKCE client, allowed redirect/logout origins, `tenant_id` claim and approved application roles. Build the web image with the final `VITE_OIDC_ISSUER`/`VITE_OIDC_CLIENT_ID`; changing Helm OIDC values does not rebuild browser configuration. A single live customer tenant must match OIDC, `AWS_TENANT_ID`, customer module tenant and resource tags.
- Select an EU registry; publish reviewed backend, economics and web image digests and pin ClickHouse/Temporal digests. Validate private-node pull access and amd64 compatibility. Choose existing Kubernetes Secrets or an approved secret-delivery controller. Bootstrap separate DB identities/Temporal databases, RDS CA and all role-specific Secrets described in `deployment.md`. Read-only onboarding does not require customer execution credentials; inert internal signer/executor services still use independent application tokens.
- Approve raw/audit COMPLIANCE retention before uploading anything (defaults 90/365 days). Lock expiry does not remove objects. No automatic S3 version expiry is configured. Keys, retained disks, snapshots, logs and state can keep costing money after application teardown. Keep the keys readable for the evidence lifetime.
- EKS uses separate, renewable IRSA identities for ingester and executor. Never give the API/worker cloud credentials. Only the ingester may assume the customer read role initially; enable the separately scoped executor trust later. Verify identity renewal throughout the restoration obligation. A short exported operator session is not the workload credential path. Local Compose remains a developer fixture environment.

## Read-only first

1. Complete local tests, Terraform validation, mock-provider tests, strict Helm rendering and credential-isolation checks. Check actual AWS quotas, supported EKS/addon versions and expected account before preparing a saved plan; those have not been proved by local rendering.
2. New customer-role installations default to `enable_execution=false`. Only the read role is created. `execution_principal_arn` and `instance_ids` remain absent. `billing_bucket_arn=null` permits EC2/EBS/CloudWatch discovery without billing S3/KMS permissions; add bounded bucket/prefix/key access when real billing is available. Missing billing, workload units or memory does not block discovery and must block unsupported execution/savings claims.
3. Provision and inspect the platform with fixture customer data first. The hosted ingester still needs raw/audit bucket IRSA. Verify OIDC/tenant isolation, private DB TLS and restricted migrator grants, image pulls, network-policy enforcement, Temporal processing, ClickHouse facts and real immutable S3 object/version delivery. Liveness alone does not establish these results.
4. Set Helm `dataMode: aws`, exact `aws.tenantId`, customer read role, ingester IRSA and platform raw/audit buckets. Set a unique external ID through its Secret. Keep `customer_execution_role_arns=[]`, `aws.executionRoleArn`, `aws.executorRoleArn` and `health.allowedHosts` empty. Verify actual STS/inventory access and rejected mutation permissions.
5. Inject a valid bearer token into the operator process without committing it or echoing it into shell history. Set `FINOPS_API_URL` (HTTPS or authenticated localhost port-forward), `FINOPS_API_TOKEN`, `FINOPS_SANDBOX_TENANT_ID`, `FINOPS_SANDBOX_ACCOUNT_ID`, `FINOPS_SANDBOX_REGION=eu-west-1` and exact `FINOPS_SANDBOX_INSTANCE_ID`. Run `node scripts/sandbox-smoke.mjs`. Default inspection sends one authenticated dashboard GET and requires only exact live tenant/discovered AWS identity. It neither creates readiness/evidence nor requires workload mapping, economic eligibility or execution credentials.

## Review a saved Terraform plan

These are operator instructions for a separately authorised planning session. Preparing a plan queries AWS; the checker itself reads a local JSON file and never invokes Terraform, AWS, a shell or apply. Use the exact same saved plan for the final human review; regenerating it invalidates that review.

```powershell
terraform -chdir=deploy/terraform plan -out=../../work/platform.tfplan
terraform -chdir=deploy/terraform show -json ../../work/platform.tfplan > work/platform-plan.json
node scripts/check-rollout-plan.mjs --plan work/platform-plan.json --expected-account YOUR_CONTROL_ACCOUNT --region eu-west-1 --stack platform --mode read-only
# Use the independently saved customer plan and customer account for its review:
node scripts/check-rollout-plan.mjs --plan work/customer-plan.json --expected-account YOUR_CUSTOMER_ACCOUNT --region eu-west-1 --stack customer --mode read-only
```

The checker rejects delete/replacement/unknown actions, changed drift, incomplete/deferred plans, missing caller-account evidence, mismatched account/region and unguarded AWS providers. Read-only mode rejects execution trust, customer execution resources and known inline policies granting EC2 start/stop. It does not resolve unknown IAM policy expressions, prove effective IAM permissions, price resources or approve apply. The module's mock tests separately prove that fresh read-only plans create no execution role/policy. Actual AWS dry-run denial tests remain required. No bypass or apply option exists.

## Preserve existing state during this upgrade

Existing customer stacks created both roles. **Keep `enable_execution=true` with the existing execution principal and exact instance IDs on their first upgraded plan.** Supply the new account/owner/expiry inputs without changing deployed names or region. The `moved` block transfers the old execution-policy state address to `[0]`; the existing execution role keeps its map address. Retain a protected state backup and review the saved plan with `--mode execution`. It should not delete or replace either role.

An older same-account installation fails the new cross-account validation. Do not remove its restoration trust or change deployed identities to force that plan through. Keep any owned restoration running under the existing configuration, finish recovery, then prepare a separately reviewed migration to the selected two-account EKS architecture. A failed plan applies nothing.

Do not set the new default false on an existing execution installation as a shortcut to pause. Role `prevent_destroy` and the plan checker deliberately block that removal. Preserve supplied billing bucket/key values too; removing them can plan policy deletion. Pause new stops through application controls while retaining Start/Describe and durable restoration. Only after all owned stops are restored, evidence is retained and trust removal is separately approved should a dedicated decommission plan be considered. This readiness checker rejects that destructive plan rather than offering an override.

## Enable one supervised execution later

After read-only acceptance, explicitly enable the customer execution role with the trusted executor principal and a single reviewed development instance allowlist; add only that target to platform execution trust and configure executor IRSA and exact HTTPS health hosts. Verify runtime stop/start delegation, stable networking, EBS backing, no instance store/fleet/production/stop protection, tenant/opt-in tags and known marginal economics. Require fresh CLEAR incident/deployment/job signals, complete baseline evidence, schema-v2 pre-execution readiness and a separately reviewed approved plan.

Set `FINOPS_APPROVED_PLAN_ID` and `FINOPS_LIVE_ACK=STOP_AND_RESTORE_THIS_SANDBOX_INSTANCE`, then run `node scripts/sandbox-smoke.mjs --execute` only in that authorised session. The token must have at least 45 minutes remaining for a 30-minute poll plus recovery margin. Local JWT expiry parsing is only a client preflight; the API validates authentication and authorisation. The script checks the exact approved signed target, schedule and evidence IDs, fresh readiness within five minutes, unexpired plan/window, fresh workload signals and readiness recommendation. It submits that plan with If-Match/idempotency, then requests immediate restoration only after owned stop. After backend completion and cleared stop ownership, it fetches the signed schedule's current version, pauses that schedule with If-Match/idempotency and confirms it remains paused with another GET. It never pauses before the new-stop precheck. An operator pause already present is retained. Successful acceptance therefore leaves further scheduling paused after one supervised cycle; resuming requires a separate deliberate operator action. It does not approve plans or refresh readiness automatically.

Keep a named human available and preserve the printed execution ID. Client timeout/disconnection is not cancellation: keep worker/executor/Temporal and restoration permissions running, follow `operations.md` and reconcile provider state. If restoration succeeds but the pause conflicts or cannot be confirmed, the script fails acceptance and names the schedule to pause before another window. Prove recovery, application health and the paused schedule before declaring acceptance. Measured and invoice-reconciled savings require their real observation/finality windows and remain separate from this canary.
