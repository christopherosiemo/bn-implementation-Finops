# Isolated group program and Git artifact contracts

This package is a private fixture component for the stateless Fleet milestone.
It is not enabled by an API, signer, worker or customer pipeline. The public
Fleet-history and configuration records remain blocked. No representative EC2
resource is invented for a group, and no existing FleetPlanV4 payload, signature
or Temporal command is converted. Customer execution and verified savings remain
unavailable.

## Group identity and bounded effects

`internal/fleetgroup` uses two exact group selections, including tenant,
workload, account, Ireland region, ASG ARN and immutable registration,
declaration and sealed-scope references. The only accepted realm is
`ISOLATED_FIXTURE`, pinned to a fixture generation and model hash. A reference to
a declared source does not issue a trusted historical receipt. A future
repository must resolve the references, current bindings, source revocation and
independent model observations before producing any executable program.

The model distinguishes candidate capacity, traffic movement and old-capacity
drain. For twenty original replicas under a ten-percent initial limit, at most
two candidates can be introduced initially. Expansion does not enlarge the
simultaneous-change allowance. Parent, forward child and owned inverse use
separate signature domains. An inverse requires an immutable applied-effect
receipt and the exact before/after models. A future durable store must also prove
that ownership is current and unconsumed; possessing an old receipt is
insufficient.

The initial Git-owned artifact gate is deliberately limited to the exact current
head and state of one applied child. It does not authorize reversing earlier
children after later forward or inverse commits. A complete authenticated owned
transition journal is required to establish that lineage and compose a whole
program rollback; a newer same-model commit alone cannot satisfy it.

The default stage policy includes a full hour of canary observation and
fifteen-minute expansion windows. Across the twenty-six independent operations,
the observation requirements total 160 minutes. The model reserves an additional
five minutes per operation for dispatch, yielding a minimum program budget of
290 minutes. A component test that applies Terraform quickly does not satisfy
these real-clock health windows.

## Artifact capture

The original schema-5 component pins one Git/configuration context. Its lab uses
real Git and pinned Terraform with three built-in `terraform_data` resources.
It validates native saved-plan ZIP contents, `show` output, state lineage/serial,
resource IDs, model changes and exact artifact hashes. It is a fixture mapping;
the built-in resources do not attest customer ASGs or listener rules. The
single-context contract cannot represent Git-owned per-stage desired changes.

The additive Git-owned family is a separate compatibility boundary. It must
approve the complete manifest of stage commits before dispatch, use committed
`main.tf.json` and `desired.auto.tfvars.json`, and obtain a fresh saved plan only
after selecting the approved revision and current state. Runtime variable
overrides, alternate configuration files and unapproved Git changes must fail
closed. Terraform accepts several variable sources with different precedence;
the isolated runner therefore controls both its environment and exact files.
See [Terraform variable precedence](https://developer.hashicorp.com/terraform/language/values/variables).

An active Git reference advances with an expected-old-value comparison, followed
by exact index/worktree checks. Git and Terraform state are separate stores;
their changes are not atomic. A future pipeline must persist command intent,
budget reservation and Git transition before applying, and reconcile an unknown
apply outcome before any retry. See [Git reference updates](https://git-scm.com/docs/git-update-ref).
Owned recovery appends a new commit on the controlled head. It must never reset
history or discard an unrelated edit. Ambiguous external changes retain the
recovery obligation for reconciliation or audited operator takeover.

Saved plans and state can contain sensitive values. The local labs retain
artifacts encrypted with authenticated run, operation, kind and plaintext-hash
context, followed by pinned readback. Their private object index records hashes,
not plaintext values or keys. No cloud credentials, host Docker socket, main
database connection or network access is given to the artifact runner. An
acceptance record is published only after validation and owned cleanup.

## Remaining connected acceptance

The component contracts and local artifact tools alone cannot establish:

- Server-resolved current 025/027 records and independently issued fixture
  history, demand, capacity and economics receipts under restricted identities.
- Authenticated proposal, independent approval and signing through actual OIDC,
  API, PostgreSQL roles and durable workflows.
- Serialized overlapping budgets, exact Git/apply intents, authenticated
  callbacks, unknown-outcome reconciliation and process recovery.
- Real-clock all-member health, independent off-instance work preservation,
  canary/expansion windows, a 35% latency regression stopping expansion and
  permanent positive-claim disqualification after rollback.
- A separate simulation ledger including surge, retained capacity, transition
  costs, negative outcomes, corrections and overlap exclusion.
- Native provider authority, customer deployment, genuine financial history,
  finalized invoices or production operational acceptance.

Those gates must pass before awarding connected Fleet maturity credit. Fixture
simulation results must stay distinguishable from customer verified savings.
