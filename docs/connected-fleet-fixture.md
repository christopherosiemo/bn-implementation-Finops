# Connected isolated fleet fixture

This increment connects existing tenant/workload fleet records to private native
preparation and independent approval. Customer execution remains disabled. AWS
identities in this local lab are explicitly provider-shaped dependencies; a
fixture does not supply missing customer history, ownership, rates or savings.

The public selection accepts two existing configuration proposal IDs and an
installed fixture profile. The server rechecks both registrations, sealed scopes,
declarations, source health and matching workload/account/region. Those customer
proposals retain their original blocked evidence. Installing an inspected local
toolchain is a private operation; migrations do not invent an installed runtime.
The shared installed-profile catalog uses bounded pages ordered by immutable ID.
Its opaque continuation is bound to the authenticated tenant and query; loading
another generation does not grant installation or execution authority.

The Linux producer uses fixed Git/Terraform binaries in an isolated workspace.
It creates a real twenty-six-entry Git manifest and a three-resource built-in
Terraform base. The private archive encrypts exact bytes, requires create-new
versioned writes, and authenticates exact-version readback before publishing
references. Seven installed-model descriptions remain labelled as descriptions;
they do not attest to observed demand, history, service health or economics.

Approval of that exact program is separate from review of the exact journal
authorization and recovery-continuation policy. Each authorization is issued
privately, exposed with its immutable canonical UTF-8 body and hash, and approved
by a different authenticated subject through the API. PostgreSQL stamps approval
time. The thirty-minute continuation review window does not extend forward
deadlines, evidence freshness, health windows or execution permission. A private
signer rechecks the current zero-record head and original forward feasibility.

Commissioned signer, ledger and pipeline public keys have a separate operator
installation boundary. The API cannot install keys or journal roots, sign
commands, submit pipeline facts, or read native plan/state bytes. PostgreSQL
enforces tenant isolation and dedicated database identities. The dedicated Go
ledger verifies signatures and transition semantics; SQL table labels alone
cannot establish signed ownership.

The journal commits command intent and a one-shot outbox entry before dispatch.
Claim expiry never makes the operation eligible for another apply. Actual native
dispatch additionally checks the current command, exact Git ref/state/saved-plan
bytes and a fresh short permit under writer and operation fences. A conflicting
working-file edit is preserved. Native dispatch markers and positive terminal
records are synchronized before being used for recovery. A missing terminal
record remains uncertain; matching old state cannot establish that no apply ran.

Read-only run inspection exposes current head hashes, event counts, owned-effect
counts, pending phases and recovery disposition through a restricted database
projection. It exposes neither command bodies nor native artifacts. An aborted
run reports a `DISQUALIFIED` inspection disposition; this is not enforcement by
a native financial ledger. No native Fleet measurement/claim integration exists.
Resolution of native duties does not assert application health or financial
verification. Public run creation remains unavailable until a commissioned
runtime can actually consume it.

Original scheduling START and owned fleet recovery remain independent of new
forward-admission requirements. New scheduling STOP, prior fleet actions and
group transitions share workload admission. Recovery-only continuation segments
retain prior effects and lifetime receipt identities; a segment limit is never
permission to discard a restoration duty.
